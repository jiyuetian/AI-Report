# 方案 B · 3.2 加载页「方案 C」：先出规则图，AI 后台增强

> 用户指定走**方案 C**。本文件先对齐"方案 C 到底是什么"，再给设计、分步实施、风险与验收。

---

## 一、三个方案的对齐（先避免误解）

| 方案 | 做法 | 用户等待体感 | AI 失败时 |
|---|---|---|---|
| **A** | AI 优先，AI 出图才落库 | 等到 AI 返回（硬超时 **180s**） | **阻塞流水线，弹框问用户**（见下方 1.2） |
| **B** | AI 优先 + 硬超时后降级规则 | 最坏等满超时 | 静默降级（用户可能不知道 AI 没参与） |
| **C（用户指定）** | **规则图秒出 → 立即看板；AI 后台增强 → 完成后升级** | **1~2 秒看到图** | **静默保持规则图，不打扰** |

现状**实际是 A + 一点 B**：有硬超时（`BRAIN_S3_LLM_TIMEOUT`），但超时/不可达时
**不会静默降级**，而是标记 `s3_ai_failed` 后**暂停流水线弹框让用户选**。

### 1.2 现状最大的体验痛点（本方案真正的价值）

`brain_run_sse.py:805-811`：

```python
if s3_ai_failed:
    choice = await _request_user_choice(run_id, {
        "stage": "S3",
        "options": ["rule_fallback", "wait_retry"],
        "reason": s3_ai_reason,
        "message": "图表推荐阶段的 AI 调用失败（模型限流或异常）。是否使用规则引擎兜底生成基础看板，还是等待 AI 恢复后重试？"
    })
```

`_request_user_choice`（`:173-180`）**默认超时 120 秒**（演示可设 `BRAIN_AI_CHOICE_TIMEOUT=30`）。

**实测配置值（`verify_32_current_state.py` 跑出来的，不是我估的）**：

| 项 | 值 |
|---|---|
| `BRAIN_S3_LLM_TIMEOUT` | **180.0 秒**（`config.py:54`） |
| 用户决策等待 | 120 秒（默认） |
| **最坏总耗时** | **300 秒 = 5.0 分钟** |

→ 初版方案里我写"等 30~60 秒"是**低估了 3~6 倍**。真实情况是：
LLM 抽风时加载页最多卡 **5 分钟**，且中途还要弹框让主持人做选择。
**这说明方案 C 不是"体验优化"而是"风险消除"。**

→ **路演现场如果 LLM 抽风，画面会停在加载页弹一个框问主持人"要不要用规则兜底"，
最多卡 120 秒。** 这是本次要消除的头号风险。

方案 C 之后：**根本不会再出现这个框** —— 规则图已经出来了，AI 只是后台增值，
失败就失败，不打断任何人。

## 三、方案 C 设计

### 3.1 状态机改造（新增 `partial` 状态）

现状 `/status` 的 status 取值：running / completed / failed / cancelled / unknown。
新增：**`partial`** —— 「规则图已落库可用，AI 增强进行中」。

```
S1 → S2 → S3-rule(毫秒) → 落库看板 v1 → status=partial  ← 前端此时跳转看板
                    ↓（同一 run 继续）
              S3-ai(后台 30~60s)
                    ├ 成功 → 生成 v2 → 更新 Dashboard.config → status=completed(enhanced)
                    └ 失败 → 保持 v1 → status=completed(rule_only)，不弹框
```

**前端改动最小化**：
- `LoadingPage.tsx:105` 的 `status === 'completed'` 判定扩为 `completed || partial`
  → 看到 partial 就 `onComplete(dashboardId)` 跳转（`setTimeout 800ms`，`:121`）
- 跳转后**继续轮询一小段时间**（复用 `startPoll`，拿到 final 状态即停）
- 看板页收到"增强完成"时弹一条**非模态**提示（不是 Modal，不打断）

### 3.2 后台增强任务

复用现有 `_run_worker`（`brain_run_sse.py:249`）后台任务机制，不引入 Celery/队列：
- 规则图落库后，`_run_worker` **不退出**，继续跑 AI 增强
- 增强结果写 `DashboardVersion`(v2, `is_auto_save=1`) + 覆盖 `Dashboard.config`
- 更新 `dashboard_config.ai_participated` → **绿标从灰变绿**（直接复用 2.4 已落地的徽标）

### 3.3 合并策略（关键设计）

AI 增强结果**不能直接无脑覆盖**，分三种粒度：

| 策略 | 行为 | 适用 |
|---|---|---|
| **追加**（默认推荐） | AI 生成的图**追加**到规则图之后，不动已有的图 | 最安全，用户已看到的图不会消失 |
| 替换 | 用 AI 图整体替换 | 演示时想要"AI 含量"最大化 |
| 择优 | AI 图与规则图按覆盖度打分，取更优的 | 理想但复杂，P2 再做 |

**默认选追加**：规则图已在用户眼前，突然被换掉会造成"我刚才看的图呢"的困惑。
演示时可通过环境变量切到"替换"。

### 3.4 冲突处理（必须有的保护）

用户在 AI 增强完成前**手动改了看板**（改标题、删图、拖布局）→ **禁止覆盖**。
判据：落库时记录的 `config_version`（或 `updated_at`）与增强任务启动时抓取的快照比对，
不一致则：
- 增强结果**仍存为 v2**（不丢，用户可在版本里查看/回滚）
- 但**不覆盖**当前 config
- 提示改为"AI 增强结果已生成（检测到你已修改过看板，未自动覆盖），可在版本历史中查看"

### 3.5 失败静默（方案 C 的核心体验）

AI 增强失败 →
- 保持规则图 v1，**不弹框、不阻塞**
- `ai_participated` 保持 False，灰标（诚实）
- 在看板页放一行可展开的灰色小字："本次 AI 增强未完成（原因：xxx），当前为规则引擎生成"
  —— 与 2.1/2.4 诚实原则一致：**不假装 AI 参与，也不让用户莫名其妙**

## 四、分步实施与工作量

| 阶段 | 内容 | 估算 |
|---|---|---|
| **P0** | 后端：S3 拆成 rule-first + ai-async；新增 `partial` 状态；AI 失败静默（**去掉弹框**） | 4~5 h |
| **P1** | 前端：`LoadingPage` 识别 partial 并跳转；跳转后继续轮询至终态；非模态提示 | 2~3 h |
| **P2** | 版本落库（v1/v2 + is_auto_save）+ 冲突检测（改过就不覆盖） | 2 h |
| **P3** | 合并策略可配置（追加 / 替换），演示环境变量 | 1 h |

**P0 单独上线就已经消除了 120 秒弹框风险** —— 这是路演前最该做的一件事。

## 五、验收标准

| # | 断言 |
|---|---|
| V1 | 点击生成后 **≤3 秒**看到看板（规则图），无论 LLM 是否可达 |
| V2 | **LLM 完全不可达时，不出现任何弹框**，看板正常生成，加载页不停留 |
| V3 | LLM 可达时，AI 增强完成后看板**追加**了 AI 图，且 `ai_participated` 由 false 变 true（灰标→绿标） |
| V4 | 增强过程中用户手动改了标题 → 增强完成后**标题保持用户改的**，不被覆盖，并给出"可在版本历史查看"提示 |
| V5 | 增强失败 → 看板保持可用，页面显示灰字说明原因，**不谎报 AI 参与** |
| V6 | 版本历史中能看到 v1（规则）与 v2（AI 增强），且可从 v2 回滚到 v1 |
| V7 | **断网演示**：全程无弹框、无卡死，评委看到的是"秒出图 + 后台悄悄变好" |

V2 与 V7 是**路演保命验收**，必须实测。

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| **图先出来又变了**（抖动） | 默认追加不替换；更新时用非模态提示 + 平滑过渡；新图加"AI 增强"角标 |
| AI 增强覆盖用户修改 | 冲突检测（P2），改过就存 v2 不覆盖 |
| 演示时 AI 增强太慢，评委看不到"变好"那一刻 | 提供"演示模式：等待增强完成再跳转"开关；或提前预热一次让模型热着 |
| 后台任务随进程退出丢失 | 增强结果落 `brain_traces` + 版本表，进程重启后可恢复/重跑；最坏情况就是保持规则图（可接受） |
| 规则图质量差，第一印象不好 | 规则引擎已有 `derived_metrics` 标注与类型标签，质量可控；且追加模式下好图不会被差图挤掉 |

## 七、路演价值（这是方案 C 最大的卖点）

1. **"1 秒出图，AI 后台悄悄变好"** —— 比"等 40 秒看 AI 表演"更打动人，
   因为它体现了**工程上的克制**：不让用户为 AI 的不确定性买单。
2. **消除 120 秒弹框风险** —— 现场最怕的就是卡住问主持人问题，方案 C 从设计上消除了它。
3. **天然可讲"优雅降级"**：AI 挂了系统照样能用，只是少了几张 AI 图 —— 这比"AI 挂了就报错"高级。
4. 与方案 O 配合更好：O 的时间轴在方案 C 下会显示"规则图已出 → AI 增强中 → 增强完成"，
   **过程可见性更强**。
