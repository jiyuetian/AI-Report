# 六层管线 + 被控提示词（控制与迭代文档）

> 版本：v1.0（2026-09-04）｜ 维护人：AI-Report 产品/研发
> 定位：本文件是「**数据管线 + 策略规则 + AI 参与节点 + 分层提示词**」的**单一可信来源（Single Source of Truth）**。
> AI 每次操作前应**先读取本文件对应节点的提示词**再介入；提示词允许在迭代中持续打磨，打磨后按「提示词登记表」的更新约定同步到运行位置，并回填底部「迭代日志」。
> 适用对象：产品、研发、数据、AI 协同轮值人员——用于对齐"产品现在能做什么、谁参与、提示词在哪、怎么改"。

---

## 一、为什么要这份文档

1. **可生长**：规则库（不依赖 AI）> AI 补充判定 > 修复管道，三层各自可独立演进，但**修复策略与检测规则必须同源**，否则出现"判可转、却置 NULL"这类一致性 bug。
2. **可控**：所有 AI 介入点都**收敛到白名单提示词**，AI 不发明清理逻辑、不臆造字段、不越权改层；提示词集中登记、版本可回滚。
3. **可对齐**：一份文档说清"每层数据在哪、策略规则是什么、AI 在哪介入、产出什么、写回哪层、提示词在哪"，参与人员看这一份即对齐迭代过程与当前能力。

## 三、数据六层总表（每层=数据 + 策略规则 + 落点 + 血缘）

> "质检/修复始终读**最上层**、只写清洗层、不动原始层" 是本管线铁律。

| 层 | 名称 | DuckDB 表 | 写入/触发方 | 该层策略规则体 | AI 介入点 | 备注 |
|----|------|-----------|-------------|----------------|-----------|------|
| L0 | 原始层 raw | `ds_{id}` | 上传解析（file/dataset） | 解析即存，不改写；列数>500 时 Top20 收敛 | 无 | 永久保留，不可覆盖 |
| L1 | 字段标准化 norm | `ds_{id}_norm` | `create_norm_from_raw()` | 复制原始层副本，供字段识别 | 无 | 备用层 |
| L2 | 清洗层 cleaned | `ds_{id}_cleaned` | `create_cleaned_from_original()` + 质量修复 | 六类质检规则 + 可生长规则库 | **AI质检（补充）** 产修复建议 → 走 coerce/fill 写回 | **修复只写本层** |
| L3 | 业务加工 processed | `ds_{id}_processed` | 业务转换 | 业务口径/规则 | 按需 | 灰色预留 |
| L4 | 聚合计算 agg | `ds_{id}_agg` / `pre_aggregate()` | 聚合缓存 | 聚合口径 | 无 | 通用聚合 |
| L5 | 看板输出 output | `ds_{id}_output` / `Dashboard.config` | `brain_run_pipeline()` S4+S5 后保存 | 看板 config 结构与标题 | **AI目标/图表/意图** 影响输出构成 | 输出到 Dashboard 表 |

**血缘服务**：`core/lineage_service.py`（`build_lineage_for_dataset` / `save_lineage_to_db` / `verify_lineage_consistency`）记录并校验上述六层血缘。

## 六、分层提示词（被控提示词 · 可编辑更新）

> 每条提示词 = 一段可直接被 AI 读取/注入的文本。**改这里 → 同步到第五节登记的运行位置 → 回填迭代日志**。
> 提示词共同底线：不臆造字段、只给出**白名单修复策略ID**、不越权改层、结构化 JSON 输出。
> **读取机制**：节点执行前经 `core/prompt_loader.py` 的 `load_prompt(slug, default, **tokens)` 读取 `prompts/{slug}.md`；文件缺失/异常时自动回退到代码内置默认，不影响运行。改 `.md` 即改行为（mtime 缓存，改文件自动重载）。

### 节点1 · AI 数据质量检测（写 L2 清洗层修复建议）

```text
角色：你是专业的数据质量分析师。
任务：分析数据集，识别【规则检测无法覆盖】的问题。
前置输入：已由规则引擎检测出的问题清单 + 各字段统计（非空/空值率/唯一值/样例值）。
检测维度：
  1 数据分布异常（离群值）
  1.5 类型一致性[重点]：是否存在"文本型数字"（如 1,234 / ￥100 / "5000" / 混入 N/A、未填写 导致整列被读成文本）？
       判定这些列【应否转向真正的数值】；编号/标识列（如借据编号 123456）应保持文本、不转数值，避免误判。
  2 语义异常  3 字段关联矛盾  4 编码异常  5 完整性  6 其他
分级：blocking=严重影响后续分析且无法忽略；warning=建议关注不阻断。
修复要求：每个问题≥2个修复选项；类型一致性里【确应转数值】的列必须给出 strategy=coerce_numeric 的"强制转数值"；
         判定为编号/标识的列【不要】报告为类型问题。
输出：JSON = {issues:[{column,severity,message,detail,row_count,sample_values,repair_options:[{strategy,label,description}]}]}
```

**与规则库的协同**：`quality_checker._check_type_consistency()` 规则优先处理高置信文本型数字（脏值占比≤`_NUMERIC_DOMINANT_RATIO=0.3`→阻断强转；可转率<`_NUMERIC_RATIO=0.5`→交 AI 裁定）。可生长常量：`_NUMERIC_SUFFIXES / _NUMERIC_RATIO / _NUMERIC_DOMINANT_RATIO`。

### 节点2 · 主题识别（S1，LLM 兜底）

```text
角色：数据分析主题识别器。
任务：根据字段清单识别数据集的业务主题（担保风控/逾期/地区分布/客户画像/产品分析 等）。
输出：JSON = {theme_tag, confidence(0-1), reason}
```

### 节点3 · 分析目标生成（S2）

```text
角色：数据分析目标规划师。
输入：主题 + 字段。
任务：生成 3–5 个业务化、中文表达、可落图的分析目标。
输出：JSON = {goals:[{goal_id,title,description,type,priority,expected_charts}]}
```

### 节点4 · 图表主生成（S3）

```text
角色：BI 图表架构师。
输入：分析目标 + 真实字段清单（含 schema 语义增强结果）。
约束：仅用给定字段，严禁臆造；chart_type ∈ {kpi,line,bar,pie,scatter,table}；生成≤5图；
     宏观粒度禁止明细表；受 s3_chart_rules.yaml 的 KPI/趋势/对比/分布/关联/明细规则约束。
输出：JSON = {charts:[{chart_type,title,x_field,y_field,category_field,value_field,config,reason}]}
```

### 节点5 · 图表增强优化（S3）

```text
任务：优化现有图表标题、描述、config，使其更贴合业务语义。
约束：保持 chart_type 与字段不变，仅优化表达与配置。
输出：与输入同构的 charts JSON 数组。
```

### 节点6 · 字段语义标注（SchemaEnricher）

```text
任务：为每个字段输出语义标注，供图表选字段。
输出：JSON = {fields:[{name,type,business_role,distribution_ok,chart_hint,cardinality,priority}]}
```

### 节点7 · 意图分类（对话修改）

```text
角色：看板修改意图识别器。
任务：把用户指令归类为 change_chart/add_chart/delete_chart/reorder_chart/filter_drill/attribution/edit_title/unknown。
输出：JSON = {intent_type,confidence,analysis:{raw_message,extracted_params,classified_by}}
```

### 节点8 · 全局 System Prompt（所有 LLM）

```text
你是一个专业的数据分析助手，必须以 JSON 格式返回结果。
```

## 七、提示词读取与更新机制（怎么让它"可控可迭代"）

1. **集中登记**：所有 AI 节点提示词在第五节登记，约定运行位置（`config_key=…` 或 `prompts/*.md` 或内联）。每条唯一编号（节点1~8）。
2. **AI 先读提示词**：任何 AI 介入前，先读取对应节点提示词（=契约），再产出结构化结果；产出必须落在白名单修复策略/输出结构内。
3. **配置化热更新**：`brain_configs` 表以 `config_key/category/content/version/is_active` 支持版本化配置，`BrainConfigManager.get_config()` 读 Redis→DB，`brain_v2.py` 提供 `/configs/{key}` 读取/更新/`history`/`rollback`。
   - 现有配置键：`theme_dict`、`goal_prompt_v1`、`chart_rules`、`orchestrate_rules`、`score_weights`（策略规则走 DB 版本化）。
4. **提示词外置（已落地）**：节点1（AI质检）、节点4（S3图表主生成）的提示词已外置为 `prompts/ai_quality_checker.md`、`prompts/s3_llm_main.md`，经 `core/prompt_loader.py` 加载（缺失回退内置默认 + mtime 缓存自动重载）。质检阈值/尾缀单位常量仍在 `quality_checker.py` 底部可生长规则库，改阈值=改行为，需登记。
5. **版本记录**：文件外置用 git 做版本追溯；配置类（`theme_dict`/`goal_prompt_v1` 等）继续走 `brain_configs` 版本化 + `version_manager`（含 `prompt_version` 快照）支持回滚。
6. **回归自测**：改提示词/规则后，运行 `backend/_verify_prompt_externalize.py`（占位符替换校验）+ `backend/_verify_type_consistency.py`（类型链路）等，再走 README 第八章四层验收。
