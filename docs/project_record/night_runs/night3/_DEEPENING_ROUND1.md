## 为什么有这一轮

第一轮 5 项代码任务（A/D1/D2/E1/E2）的 git 提交时间戳显示：每项实际耗时仅 **4~7 分钟**
（1bdc645=23:10:51 → 96050cd=23:32:31，5 项共 22 分钟）。任务卡初版写的 17~25 分钟是体感估算失真。

距离「能改的每项 ≥20 分钟」差距很大，因此启动本轮：**不做新任务，回头对自己做过的每一项用反例攻击**，
把"看起来做完了"变成"边界也站得住"。

## 方法

对每一项问三句：
1. 这项真做到位了吗？（有没有只解决了一半）
2. 边界情况都覆盖了吗？（真实数据的脏写法有没有考虑）
3. 还能再加深度吗？（能不能从人工审计升级为机器可复跑的资产）

每条发现必须有**可追溯的反例来源**（后端代码 / 真实数据形态），不许凭感觉补。

## A. 3.1 上传页布局（首修 1bdc645 23:10:51 → 深补 fee2792 23:44:40）

### 反例
上一版只把 Dragger 收缩成一行。但 `UploadPage.tsx:921` 的「上传队列」Card **无条件渲染整个 List**：
N 份文件 = N 个 `List.Item`。N=10 时约 720px，首屏照样被占。
→ 用户要求的是「上传后收缩**不占第一屏**」，我只做了一半。

### 补充
- `queueCollapsed = 有文件 && 无 uploading/error && 未手动展开`
- 边界：只要还有 `uploading`（要看进度条、取消）或 `error`（要点重试）就**必须保持展开**
  —— 否则「重试」按钮被藏起来 = 功能丢失
- 收缩态一行「上传队列 · N 份文件，全部完成」+ 展开；展开态右上角「收起」

### 证据
`defect_fix_evidence/final_fixes/test_31_queue_collapse.js` — 9 用例 ALL PASS，含 2 个关键反例（有 uploading / 有 error 不得收缩）。
首屏收益：N=10 节省约 672px，N=20 节省约 1312px。

## D2. 3.5 AI 归因实查（首修 76d3c8c 23:24:20 → 深补 154255f 23:40:30）

### 反例
真实 Excel 导出列名常带首尾空格 / 全角空格（`" 抵押率 "`）。旧实现用 `field_index.get(name)` 精确匹配
→ 一律判 `missing`（假阴性），AI 会误报"字段不存在"，等于换了个花样继续误导用户。

### 补充
- `_norm`（trim）/ `_squash`（去半角+全角空格）/ `_lookup`（精确 → 去空格 → 大小写不敏感）三级归一化

### 我自己引入的回归（并修掉）
加深时把「原名」和「去空格别名」都塞进 `field_index`，导致 `len(field_index)` 被重复计数：
所有对外话术里的「已实查 N 个字段」虚高，且样例字段列表可能吐出去空格后的怪名字。
→ 拆出 `field_names` 只存原名，专供计数/举例；`field_index` 只做查找。

### 证据
`test_35_attribution.py` 从 6 用例扩到 **12 用例**：
新增 7=首尾空格 / 8=配置带空格（反向）/ 9=全角空格 / 10=大小写 / 11=**防假阳性**（真不存在的字段仍须 missing）/ 12=**计数不被别名污染**。
12/12 ALL PASS，旧话术「请先刷新看板页面」出现 0 次。

## E1. 3.6 管理后台设置页（首修 f4cacf5 23:28:23 → 深补 3170f3b 23:50:53）

### 反例（三个缺口）
1. **loading 与 unknown 同态**：慢网络下请求还在飞，页面显示「状态未知（健康检查未返回）」
   —— 把"正在检测"说成"接口没返回"，仍是失真，违背 2.1/2.4 诚实原则。
2. **永不刷新**：antd5 Tabs 默认 `destroyInactiveTabPane=false`，SettingsTab 保持挂载，
   `useEffect([])` 只跑一次 → LLM 恢复可达后回到设置页仍显示「不可达」，不会自愈。
3. **取值过严**：`typeof v === 'boolean'` 只认布尔。后端若返回 `0/1/"true"/"false"`，
   会把「不可达」误报成「未知」。

### 补充
- 四态：检测中(loading) / 可达 / 不可达 / 未知，并展示检测时间
- 新增「重新检测」按钮（解决 Tabs 不重挂）
- 取值兼容布尔 / 数值 / 字符串三形态；无法判定仍归「未知」不谎报

### 证据
`test_36_health_state.js` — A12+B1+C5+D2+E5 全通过。
实测旧逻辑对 **6 种取值形态全部误报为「未知」**（1/0/"true"/"false"/"1"/"0"）。

## 本轮共性教训

1. **"改了一半"是最常见的假完成**：A 项只收 Dragger 没收队列，最典型。验收要回到用户的原始措辞
   （"不占第一屏"）逐字对照，而不是对照我自己拆的子任务。
2. **前端判定必须对齐后端的脏数据容忍度**：D1、D2 两个 bug 同源 —— 前端做了严格相等，
   后端却有归一化。以后改前端判定前，先 grep 后端同名枚举的归一化表。
3. **加深时引入回归是真实风险**（D2 别名污染计数）。加深完必须重跑测试，且要加防回归用例。
4. **人工审计要升级为机器资产**：E2 的扫描器以后每次提交都能复跑，比"我审过了"有价值得多；
   但机器判据要配自测，否则静默失效比不做更糟。
5. **Edit 工具在本仓库多次静默失败**（返回 Success 但未落盘）。本轮全部改用
   Python 脚本 + `assert count==1` + 落盘后 Read 校验，未再发生。
