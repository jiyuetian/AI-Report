## 关键发现

### 发现 1：S3 完全没有样本数据注入

已确认 `s3_llm_enhancer.py` 全文**不含 `sample` 字样** —— S3 是唯一完全不注入样本数据的 AI 阶段
（S1 注入 `sample_data[:3]`、S2 注入 `sample_data[:3]`、AI 质检注入 50 行）。

`fields_desc` 只有「字段名 + 类型标签 + 业务角色 + 建议」，**没有取值、没有基数、没有空值率**。
由此导致三个具体问题：臆造字段名 / 基数病态（拿客户名做饼图）/ 编造筛选值。

### 发现 2（更正初版）：材料其实链路上已经算出来了

初版写"只需要补 distinct 计数与取值采样" —— **低估了现状**，已更正。逐项核实：

| 材料 | 现成位置 | 状态 |
|---|---|---|
| distinct 计数 | `brain_run_sse.py:1051` `SELECT COUNT(DISTINCT "{_d}")`，入参 `column_cardinality`(:90) | ✅ 已算出 |
| 取值样例 | `ai_quality_checker.py:108` `sample_values[:5]` | ✅ 已算出 |
| 空值率 | `ai_quality_checker.py:106`、`field_profiles` | ✅ 已算出 |
| 现成画像文案模板 | `ai_quality_checker.py:123-127`「非空X/Y行, 空值率Z, 唯一值N个, 样例:[...]」 | ✅ 可复用 |

→ **P0 成本低于初版估算**：不需要新建画像体系，主要是把已有能力接到 S3 的 `fields_desc`。

### 由此提炼的核心论点

`brain_run_sse.py:1051` 的 DISTINCT 是**生成之后**算的，用途是**事后消毒**（见方案 P 的 1.1b）。
→ Q 的核心动作是**把这个已有能力前移**：从「生成后算基数、不合格就丢」
变成「生成前把基数告诉 LLM、让它别选错」。
**事前预防比事后丢弃更划算 —— 被丢弃的图不计入 AI 参与率，预防选对则会。**

这条也把 Q 与 P 连成了一个闭环：同一个 `column_cardinality`，事后用 = P 的消毒，事前的用 = Q 的注入。
